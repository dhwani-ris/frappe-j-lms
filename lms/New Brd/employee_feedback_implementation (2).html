Employee Feedback Form

A single form, auto-created when an employee completes 100% of an assigned course. The immediate manager and a master trainer each give feedback once; every assigned trainer gives feedback through a child table (the trainers are pre-filled from the course assignment). Reviewers work in the Jamboree portal; a controller-driven status walks the form from Draft to Completed and locks it, firing notifications at each stage.

1 · Overview

When an employee (for example, Kashish Talwani) reaches 100% completion of an assigned course, one Employee Feedback Form is created for that employee and course. The employee, course, immediate manager and the assignment batch sit at the top of the form (employee name, course title and immediate manager auto-fetch). A Master Trainer first schedules all the meeting times — the manager's, each trainer's and their own — and only then can the reviewers fill their feedback. Because more than one trainer can run mock sessions, trainers are rows in a child table, and because the trainers were already chosen when the course was assigned, those rows are pre-filled automatically from the assignment. A controller walks the form from Draft → Sessions Scheduled → Completed, firing notifications at each stage.

Course assignment already works this way in Jamboree: lms/lms/custom/course_assignment.py::assign_course_to_student() creates a one-student “micro-batch”, attaches the course, and stores the chosen trainers as Course Instructor rows on that LMS Batch. The feedback form reuses exactly that data.

3 · Status Lifecycle CHANGED

There is no desk Workflow and the doc is not submittable. The status field is driven entirely by the controller (employee_feedback_form.py) and the whitelisted portal actions (employee_feedback.py). The flow is now schedule-first: a Master Trainer sets every meeting time before any feedback can be entered.

Scheduling rules (enforced on schedule_sessions): the MT may add multiple manager and master sessions (≥1 manager when the employee has a manager; ≥1 master). Every session time must be present and in the future; the order is strict by group — all manager sessions < all trainer sessions < all master sessions, each group in row order; each consecutive pair ≥15 minutes apart; and no participant (matched by their User) may already have a feedback session whose 15-minute block overlaps on another not-Completed form — else "… already has a feedback session scheduled around …".

Feedback opens only after scheduling. The save_* actions reject edits until sessions_scheduled is set. Meeting times are owned by the Master Trainer and locked once confirmed — changing them requires a reschedule (back to Draft). Complete is gated on the manager (if any), every trainer row and the master being recorded; a completed form is locked until an admin reopens it.

Feedback recording is unordered. Once the sessions are scheduled, the manager, trainers and master trainer may record their feedback in any sequence — the states are a progress indicator, not a gate. The only ordering enforced is on the meeting times (above), not on who writes feedback first. The single hard gate is Complete.

5 · Roles, Permissions & Visibility

A form is visible only to the people tied to it (employee, manager, trainers) plus admins / master trainers. A general learner with no form sees nothing. Scoping reuses the existing Jamboree roles and the permission-hook pattern from batch_enrollment_approval.py.

  • Row-level scoping via permission_query_conditions → employee_feedback.get_permission_query: a user sees a form if they are the employee, the immediate manager, or appear in the trainer child table (a sub-query on Employee Feedback Trainer.trainer). Admins and master trainers see all. Mirrored by has_permission for single-doc access.
  • Role perms live on the DocType and are replicated as Custom DocPerm in jamboree_setup.py. LMS Student gets read-only CHANGED — the query then limits a student to only their own form (as the evaluatee), so a general learner still sees nothing. The evaluatee’s read-only view is reinforced by the capability flags (all can_edit_* false), and the whitelisted actions enforce per-action checks (e.g. only a master trainer may complete).
  • User Permissions bypassed on the Employee links CHANGED: employee and immediate_manager carry ignore_user_permissions: 1. Jamboree sets a per-employee User Permission (Employee = self) on each user; without this flag Frappe would AND that restriction onto every Employee-linked doctype and hide a form from its own trainers / manager / evaluatee. Visibility is governed solely by the permission query above.

6 · Portal Delivery (frappe-ui) CHANGED

Reviewers act in the existing Jamboree portal, not the desk. The original Module Def / Workspace / sidebar / Desktop Icon setup is not used; the DocType lives in the LMS module purely as the backing store.

  1. Route /feedback/:name → EmployeeFeedbackForm.vue. It loads get_feedback_form(name), which returns the form plus per-user capability flags (can_schedule, can_reschedule NEW, can_edit_manager, can_edit_trainer, can_edit_master, can_complete, can_reopen, is_readonly) plus sessions_scheduled and master_trainer.
  2. Schedule panel NEW: when can_schedule (Master Trainer / admin, form still Draft) the page shows date-time pickers for the manager (if any), every trainer and the master, and a Confirm Schedule button (schedule_sessions). Order/gap/conflict errors come back from the controller and surface via toast. Once scheduled, a Reschedule button (reschedule_sessions) is shown instead.
  3. Feedback sections stay locked until sessions_scheduled. After that, each is editable only per the flags: the manager block for the manager, the caller’s own trainer row, the master block + Complete & Submit for the assigned master_trainer; the scheduled meeting time is shown read-only in every section. Everything else is read-only.
  4. EmployeeFeedbackList.vue (a “Pending Feedback” card) is embedded in the Trainer Dashboard, Manager Dashboard and Employee Detail pages, calling list_my_feedback_forms and surfacing items that need the user’s action first.
  5. Left-menu link NEW: a Management → Employee Feedback item (src/utils/index.js) routes to /feedback → EmployeeFeedback.vue, a full-page list of every form the user can act on (or view). Shown to all reviewers, and to an evaluatee only when they actually have a form — gated by canSeeEmployeeFeedback() using a new has_employee_feedback flag on get_user_info.
  6. The evaluatee opens their own form read-only via the same route (allowed by the permission query; every edit control is hidden by the capability flags).
  7. A small desk client script (employee_feedback_form.js) exposes Complete / Reopen buttons for admins who work in the desk.

7 · Controller Logic

Auto-creation on course completion

  • Hooked on LMS Enrollment.on_update → employee_feedback.create_feedback_form_on_completion (alongside the existing completion notifier). When progress >= 100: resolve the active Employee for the learner, resolve the assignment micro-batch (the batch the member is enrolled in that carries the course), and create one form with employee, course, batch, completed_on.
  • Assigned-employees only: if the learner is not an active Employee, or has no assignment batch (e.g. self-enrolled), no form is created.
  • Uniqueness on employee + course — the same completion can’t spawn two forms.
  • Trainer rows pre-filled from the batch’s Course Instructor rows.

Scheduling rules NEW

  • schedule_sessions sets every meeting time, self-assigns master_trainer, runs the cross-form conflict check (_busy_blocks / _check_conflicts, skipping Completed forms), then saves with flags.scheduling; validate_schedule() enforces all-present + future + strict order + ≥15-min gaps; on success sessions_scheduled = 1 and the status moves to Sessions Scheduled.
  • Meeting times are locked after confirm: a tamper-guard in validate() throws if any datetime changes on a scheduled form outside a (re)schedule. reschedule_sessions sets flags.rescheduling → back to Draft with times editable; feedback is preserved.

Feedback & completion rules

  • validate(): set each session/row’s recorded (and stamp recorded_by/on) when its (MT-set) date + feedback are filled; recompute status (which starts at Sessions Scheduled once scheduled). A role is "done" when all its sessions are recorded.
  • The save_* actions reject feedback until sessions_scheduled, and target a specific session row. Master feedback + completion are restricted to the form's assigned master_trainer (or an admin).
  • Block Complete unless every manager session (when the employee has a manager), every trainer row, and every master session are recorded — otherwise frappe.throw(...).
  • Status is driven by the controller and the whitelisted actions, never by writing the field from the UI; a Completed form is locked until reopen_feedback.

8 · Resolved Decisions

1. Completion is read from LMS Enrollment.progress >= 100 (the same signal the existing completion notifier uses); course links to LMS Course.

2. Master trainers are org-wide by role profile (Jamboree Master Trainer) for visibility and the form-created notification, but scheduling self-assigns one CHANGED: whoever confirms the schedule is written to master_trainer and is the only one (besides admins) who can record master feedback or complete. Rescheduling re-assigns it to whoever re-confirms.

3. Trainers are pre-filled from the course assignment (the micro-batch instructors); there is no manual “assign trainers” step. Trainers are Users.

4. Reviewers (manager, trainers, master trainers) are linked to Frappe Users, so notifications route to real logins. The immediate manager resolves via Employee.reports_to → user_id.

5. One form per employee + course; only for assigned employees. Repeat assignments of the same course would need an attempt/cycle field (not in scope).

6. NEW Meeting times are owned by the Master Trainer. The MT sets the manager's, every trainer's and the master's time in a single Schedule step; no other user can edit a time. Feedback opens only after all times are confirmed.

7. NEW Ordering & gap: strict manager < trainer 1 < trainer 2 < … < master in row order, ≥15 minutes apart, all in the future.

8. NEW Conflict: each meeting is a 15-minute block; a participant (matched by User) cannot be scheduled where their block overlaps one they already have on another not-Completed form.

9. NEW No manager: if the employee has no reports_to, the manager slot is skipped (order becomes trainers < master) and completion does not require manager feedback.

10. NEW Lock & reschedule: confirmed times are locked; the MT/admin can Reschedule (back to Draft, feedback preserved, everyone re-notified).

11. NEW Multiple manager / master sessions: the manager and the master trainer can each have several sessions (own meeting + feedback) in the manager_sessions / master_sessions tables (≥1 each, manager skipped if none). The group order & ≥15-min gap apply across all of them, and a role is done only when all its sessions are recorded. Existing forms are migrated to one session row each.

9 · Roster Maintenance NEW

The roster can change after a form exists. Both paths sync the (employee, course) non-Completed form; Completed forms are never touched. If no form exists yet, the future auto-created form simply picks up the current roster.

Edit trainers — /assign-course

An "Edit Trainers" action on each assignment row opens a multi-select dialog (pre-filled with the current trainers) → course_assignment.update_assignment_trainers(batch, trainers), which rewrites the batch's Course Instructor rows and calls employee_feedback.sync_assignment_trainers_to_feedback.

  • Add a trainer → a trainer_feedback row is added; if the form was already scheduled it drops back to Draft for rescheduling. The new trainer is notified and the master trainer / HR are nudged to (re)schedule.
  • Remove a trainer → the row (and its slot) is dropped only if not yet recorded; a trainer who already gave feedback is kept. Removal-only changes keep the existing schedule (a syncing_roster flag bypasses the locked-times guard).

Change manager — /employees/:id

dashboard_api.update_employee_manager sets Employee.reports_to then calls employee_feedback.sync_manager_to_feedback:

  • On each non-Completed form, if no manager session is recorded → set immediate_manager to the new manager (keeping the scheduled manager session times); the new manager is notified. If manager feedback is already recorded → leave it unchanged.
  • Removing the manager clears manager_sessions (no one to attend).
  • immediate_manager uses fetch_if_empty: 1 CHANGED so it's pinned at creation and isn't silently re-fetched on later saves — without this the "don't change once feedback is saved" rule couldn't hold.
